# Falak POS — السحابة المشتركة: ماذا قررنا، وهل نحتاج Supabase، وكيف نحسّنها

> الملف 6 · يكمّل الملف 02 (§7–§10) والملف 04 (المرحلة M4). يثبّت قرار البنية السحابية بعد مناقشة Supabase.
> القرار المختصر: **نعم، نستخدم Supabase كقاعدة البيانات السحابية المُدارة (+ Auth + Storage)، ونُبقي منطق الترخيص والمزامنة والإصدارات في خدمة Node.js خاصة بنا. الأجهزة لا تتصل بـ Supabase مباشرة أبداً.**

---

## 1. ما قررناه حتى الآن (تلخيص)

| الطبقة | القرار | لماذا |
|---|---|---|
| عند العميل | PostgreSQL محلي + وكيل Node.js + نافذة Tauri | البيع بدون إنترنت، عدة كاشيرات على شبكة المحل، أيقونة وتثبيت بنقرة |
| مصدر الحقيقة | جهاز المحل الرئيسي | السحابة مرآة للتقارير والنسخ الاحتياطي، لا تُعطّل البيع |
| السحابة | PostgreSQL بنفس المخطط + `tenant_id` + RLS، وخدمة API (Fastify) | ترخيص JWT موقّع (EdDSA) صالح 7 أيام بنبضة كل 6 ساعات، استقبال `sync_outbox`، توزيع إصدارات موقّعة، نسخ احتياطي مشفّر |
| لوحات | لوحة فلك الداخلية + لوحة المالك (PWA قراءة) | التحكم بالاشتراكات والأجهزة والتحديثات، وأرقام اليوم من الموبايل |
| الحماية | القيمة التجارية على السحابة، والترخيص مربوط ببصمة الجهاز | الكود المحلي قابل للكسر نظرياً، السحابة لا |

ما لم نكن قد حسمناه: **من يشغّل PostgreSQL السحابي ومن يحمي النسخ الاحتياطية ومن يبني المصادقة للوحات؟** هذا ما يجيب عنه سؤال Supabase.

## 2. هل نحتاج Supabase؟

Supabase = PostgreSQL مُدار + مصادقة (Auth) + تخزين ملفات (Storage) + Realtime + Edge Functions + لوحة إدارة (Studio) + نسخ احتياطي يومي. نحن نحتاج بالضبط: Postgres مُدار، مصادقة للوحتين، تخزين للنسخ الاحتياطية والحزم والصور. أي أن ثلاثة أرباع ما نحتاجه على السحابة موجود جاهزاً.

### 2.1 المقارنة

| | Supabase (Pro) | Postgres على VPS ندرها بأنفسنا | Neon (Postgres serverless) |
|---|---|---|---|
| الكلفة الشهرية (سنة 1) | $25 + استهلاك (≈ $25–40) | $20–45 VPS + وقت الفريق | $19 + استهلاك |
| إدارة القاعدة والنسخ والترقية | مُدارة، نسخ يومي (PITR بإضافة) | علينا: تثبيت، تحديث، مراقبة، نسخ، استعادة | مُدارة |
| المصادقة (Auth) | جاهزة: بريد/هاتف/OTP، JWT | نبنيها (أسبوع عمل على الأقل) | نبنيها |
| تخزين الملفات | جاهز (S3 داخلي مع سياسات RLS) | نستأجر S3/R2 ونربطه | نستأجر |
| RLS للمستأجرين | نفس Postgres، تعمل | تعمل | تعمل |
| Realtime (لوحة فلك تشاهد النبضات حيّة) | جاهز | نبنيه (WebSocket) | لا |
| القرب من فلسطين | Frankfurt (eu-central-1) ≈ 60–90ms | نختار Hetzner Falkenstein ≈ نفس الزمن | Frankfurt |
| الاحتباس (Lock-in) | منخفض: Postgres عادي يُصدَّر بـ `pg_dump`؛ Auth وStorage تُهاجر بجهد يومين | صفر | منخفض |
| مخاطر | حدود الخطة (8GB تخزين ضمن Pro ثم $0.125/GB)، تعليق المشروع إن لم يُدفع، الاعتماد على شركة أجنبية | شخص واحد يعرف السيرفر، نسيان النسخ، ثغرات غير مرقّعة | نفس Supabase تقريباً بلا Auth/Storage |

### 2.2 القرار
**Supabase Pro لسنة واحدة على الأقل.** السبب الحاسم: فريق من 2–3 لا يملك ترف إدارة قاعدة بيانات إنتاجية ومصادقة وتخزين ونسخ احتياطي بنفسه في أول 12 أسبوعاً، وكل ساعة تُصرف هناك تُخصم من الكاشير. والاحتباس منخفض لأن الجوهر Postgres عادي بمخططنا نفسه، فالانتقال لاحقاً لسيرفر خاص (لو تجاوزت الكلفة $150/شهر أو طُلبت إقامة البيانات محلياً) يوم عمل مع `pg_dump`.

ما **لا** نستخدمه من Supabase: Edge Functions لمنطق الترخيص والمزامنة (نُبقيه في خدمة Node واحدة نتحكم بها ونختبرها محلياً)، والوصول المباشر من الأجهزة بمفتاح anon.

## 3. البنية السحابية النهائية

```
جهاز المحل ──(HTTPS, license JWT)──► falak-cloud (Node/Fastify على Railway أو Fly.io، Frankfurt)
                                        │  /license/heartbeat   يوقّع JWT، يقرأ subscriptions/plans
                                        │  /sync/push           يتحقق ويُدرج دفعات outbox (upsert)
                                        │  /releases/latest     يعيد رابط حزمة موقّعة من Storage
                                        │  /backup/upload       يعطي رابط رفع موقّعاً لدلو المستأجر
                                        │  /catalog/lookup      الكتالوج المركزي (قراءة)
                                        ▼
                               Supabase (Postgres + RLS · Auth · Storage · Realtime)
                                        ▲                          ▲
        لوحة المالك (PWA) ── Supabase Auth (OTP هاتف) + RLS ──┘         │
        لوحة فلك (React) ── Supabase Auth (بريد) + دور falak_admin ──────┘
```

**قواعد ثابتة:**
1. **الأجهزة تتحدث مع `falak-cloud` فقط.** لا مفتاح Supabase داخل البرنامج المثبَّت عند العميل، لأن أي مفتاح هناك يمكن استخراجه. `falak-cloud` يستخدم مفتاح `service_role` من متغير بيئة على السيرفر.
2. **اللوحات (المالك، فلك) تتحدث مع Supabase مباشرة** عبر Auth + RLS، لأنها تطبيقات ويب لمستخدمين حقيقيين وهذا يوفّر بناء API للقراءة كاملاً.
3. **المخطط واحد**: نفس `falak_pos_schema.sql` يُطبَّق على Supabase مع إضافة سياسات RLS (القسم 5) وجداول السحابة (`plans`, `subscriptions`, …) التي لا تُنشأ محلياً.
4. **الخدمة `falak-cloud` بلا حالة** (stateless): كل شيء في Postgres وStorage، فيمكن تشغيل نسختين منها.

## 4. المصادقة والهويات (ثلاثة أنواع، لا تخلطها)

| من | كيف يثبت هويته | ما يصله |
|---|---|---|
| **جهاز المحل** | مفتاح ترخيص `FLK-XXXX-…` يُدخل مرة واحدة + بصمة الجهاز → `falak-cloud` يعيد JWT جهاز (EdDSA، 7 أيام) | نبضة، مزامنة، تحديثات، نسخ احتياطي، كتالوج |
| **المالك/المدير على الموبايل** | Supabase Auth بـ OTP على رقم الهاتف المسجّل في `users.phone` (أو بريد) → JWT فيه `tenant_id` كـ claim | قراءة بيانات مستأجره فقط عبر RLS |
| **فريق فلك** | Supabase Auth بالبريد + عمود `app_metadata.role = 'falak_admin'` | كل المستأجرين (سياسات RLS تسمح لهذا الدور)، وكل قراءة تفصيلية تُسجَّل |

ربط المستخدم المحلي بحساب Supabase: عند تفعيل "لوحة المالك" من إعدادات البرنامج، الوكيل يطلب من `falak-cloud` إنشاء مستخدم Supabase بنفس الهاتف ويضع `tenant_id` و`local_user_id` في `app_metadata`. لا كلمات مرور تُنسخ بين النظامين.

## 5. عزل المستأجرين (RLS) — النمط

```sql
-- على كل جدول فيه tenant_id (سحابياً فقط)
ALTER TABLE sales ENABLE ROW LEVEL SECURITY;

-- المالك والمدير: صفوف مستأجرهم فقط
CREATE POLICY tenant_read ON sales FOR SELECT
  USING (tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid);

-- فريق فلك: كل شيء
CREATE POLICY falak_admin_all ON sales FOR ALL
  USING ((auth.jwt() -> 'app_metadata' ->> 'role') = 'falak_admin');

-- الخدمة falak-cloud تستخدم service_role وتتجاوز RLS، وتضبط tenant_id بنفسها عند الإدراج
```
اللوحات لا تكتب في جداول الأعمال أبداً (قراءة فقط)؛ الكتابة الوحيدة من اللوحات هي جداول فلك (`subscriptions`, `rollouts`, …) بدور `falak_admin`.

## 6. Storage — الدلاء والسياسات

| الدلو | المحتوى | من يكتب | من يقرأ | الاحتفاظ |
|---|---|---|---|---|
| `backups/{tenant_id}/…` | `pg_dump` مشفّر على الجهاز (AES-256-GCM بمفتاح المستأجر) — **لمشتركي وحدة cloud_backup فقط** | الجهاز عبر رابط رفع موقّع من `falak-cloud` | فلك (للاستعادة بطلب العميل)، المالك (تحميل نسخته) | 30 نسخة يومية + شهرية لسنة |
| `releases/{version}/…` | حزمة التحديث + توقيع ed25519 | خط البناء (CI) | عام عبر رابط موقّع قصير | كل الإصدارات |
| `catalog/…` | صور أصناف الكتالوج المركزي | فلك + مساهمات موافق عليها | عام | دائم |
| `tenant-media/{tenant_id}/…` | شعار المحل، صور الأصناف الخاصة، صور الوصفات | الجهاز عبر `falak-cloud` | المستأجر نفسه | دائم |

## 7. المزامنة — تحسين على ما في الملف 02

1. **قسّم الجداول إلى ثلاث فئات** بدل معاملة الكل بنفس الطريقة:
   - **إضافة فقط (append-only)**: `sales`, `sale_lines`, `sale_payments`, `stock_movements`, `cash_movements`, `customer_transactions`, `supplier_transactions`, `audit_logs`, `shifts`. تُرفع بترتيب `outbox.id` ولا تتعارض أبداً. الأولوية القصوى (كل دقيقة).
   - **كيانات (upsert بـ updated_at)**: أصناف، أسعار، عملاء، موردون، مستخدمون، إعدادات. كل 5 دقائق.
   - **لا تُزامَن**: `sync_outbox`, `schema_migrations`, الجداول السحابية.
2. **الدفعة idempotent**: كل دفعة رفع تحمل `batch_id` (UUID) و`device_id`؛ السحابة تحفظ الدفعات المعالجة في جدول `sync_batches` فلا تُطبَّق مرتين لو انقطع الاتصال بعد الإرسال وقبل الرد.
3. **ضغط**: الحزمة JSON مضغوطة gzip؛ 500 فاتورة ≈ 150KB.
4. **مراقبة التأخر**: النبضة تحمل `pending_rows` وأقدم `created_at` غير مرفوع؛ لوحة فلك تلوّن الجهاز كهرمانياً إن تجاوز التأخر 24 ساعة وأحمر إن تجاوز 3 أيام.
5. **الاتجاه العكسي محدود ومُعلَن**: الترخيص والوحدات، تعطيل مستخدم، تغيير باقة، والكتالوج عند الطلب. لا تعديل أصناف من السحابة في الإصدار الأول (يمنع تعارضات لا نملك أدوات حلها بعد).

## 8. تفعيل العميل الجديد (Onboarding) — التسلسل المعتمد

1. C ينشئ المستأجر من لوحة فلك: الاسم، نوع النشاط، الباقة، تاريخ الانتهاء ← يظهر **مفتاح ترخيص** واحد لكل جهاز مسموح.
2. المثبّت على جهاز المحل ← شاشة الإعداد الأول ← إدخال المفتاح ← الوكيل يرسل (المفتاح + بصمة الجهاز) ← `falak-cloud` يربط الجهاز ويعيد JWT + الوحدات.
3. **لو لا إنترنت وقت التركيب:** C يفعّل من نقطة اتصال هاتفه (يحتاج 10 ثوانٍ اتصال). لا نبني "تجربة بلا اتصال أبداً" لأنها تفتح باب النسخ.
4. الوكيل يبدأ النبضات والمزامنة تلقائياً. المالك يفعّل لوحة الموبايل من الإعدادات (OTP على هاتفه).

## 9. المفاتيح والأسرار

| السر | أين يعيش | التدوير |
|---|---|---|
| مفتاح توقيع التراخيص (ed25519 خاص) | متغير بيئة في `falak-cloud` (Railway/Fly secrets)، نسخة مشفّرة في خزنة خالد | سنوياً؛ البرنامج يحمل **قائمة** مفاتيح عامة (الحالي + السابق) ليقبل الاثنين أثناء التدوير |
| مفتاح توقيع الحزم (ed25519) | CI فقط (GitHub secret) | سنوياً بنفس الأسلوب |
| `service_role` لـ Supabase | `falak-cloud` فقط | عند أي شك |
| مفتاح تشفير النسخ الاحتياطية | يُولَّد على جهاز العميل عند التثبيت، يُعرض للمالك مرة (QR) ويُخزَّن عنده؛ نسخة مشفّرة بكلمة مرور المالك في السحابة | لا يُدوَّر؛ فقدانه = فقدان النسخ القديمة (يُشرح للمالك) |
| شهادة توقيع كود ويندوز | جهاز البناء + CI | حسب صلاحيتها |

## 9.5 النسخ الاحتياطي السحابي كخدمة مدفوعة (قرار)

- وحدة `cloud_backup` تُفعَّل لكل مستأجر على حدة (add-on بـ $5/شهر أو $50/سنة — الملف 05 §3.1)، وتظهر في JWT الترخيص ككل الوحدات.
- **الجميع** يحصل على النسخ المحلي كل ساعة؛ الوكيل يرفع النسخة الليلية **فقط** إذا حمل الترخيص `cloud_backup`.
- في شاشة الإعدادات لمن لم يشترك: بطاقة تشرح الخدمة بجملة "لو سُرق الجهاز أو احترق، نسختك عندنا" وزر "اطلب التفعيل" يرسل طلباً للوحة فلك.
- عند إيقاف الخدمة أو انتهاء الاشتراك: النسخ الموجودة تُحفظ 90 يوماً ثم تُحذف، ويُنبَّه العميل قبلها (لا نحتجز بيانات أحد).
- كلفة التخزين علينا ≈ $0.03–0.10 لكل عميل شهرياً، فالهامش شبه كامل.

## 10. المراقبة والتنبيه لفلك

- **Sentry** في الوكيل والواجهة (الأخطاء تُخزَّن محلياً وتُرسل عند الاتصال) وفي `falak-cloud`.
- استعلام مجدول (cron في Supabase أو في الخدمة) كل ساعة: أجهزة بلا نبضة 24 ساعة، مزامنة متأخرة 3 أيام، اشتراك ينتهي خلال 7 أيام، فشل تحديث → صف في `notifications` سحابي + رسالة واتساب/بريد لفلك.
- لوحة فلك تشترك بـ Realtime على `heartbeats` لعرض حالة الأجهزة حيّة.

## 12. اقتراحات تحسين أخرى (خارج Supabase)

1. **جدول `sync_batches` + `batch_id`** كما في §7 — يُضاف للمخطط في الترحيل 0002.
2. **تجميع البيانات القديمة سحابياً**: بعد 13 شهراً تُنقل أسطر الفواتير إلى جدول ملخّص يومي لكل صنف؛ التفصيل يبقى على الجهاز وفي النسخ الاحتياطية. يبقي قاعدة Supabase صغيرة ورخيصة.
3. **الكتالوج المركزي كمخطط منفصل** `catalog.products` بقراءة عامة عبر `falak-cloud` وكاش محلي؛ المساهمات من العملاء تدخل `catalog.suggestions` وتُعتمد من لوحة فلك قبل أن تصبح عامة.
4. **لوحة المالك تُبنى قبل لوحة فلك** في M4 (يومان) لأنها حجة بيع، بينما لوحة فلك في أول شهرين يمكن أن تكون Supabase Studio + استعلامات محفوظة.
5. **وضع "قراءة فقط عند الاشتراك الموقوف"** يُطبَّق في الوكيل بحقل `mode` في JWT: `full | read_only | blocked` بدل منطق موزّع في الواجهة.
6. **اختبار كارثي شهري**: استعادة نسخة احتياطية لمستأجر عشوائي على جهاز اختبار، وتوثيق الزمن. يُدرج كمهمة متكررة في التقويم من الشهر الأول بعد الإطلاق.
7. **نسختان من `falak-cloud`** خلف موازن Railway/Fly من اليوم الأول (كلفة $5 إضافية) حتى لا يتوقف الترخيص أثناء نشر تحديث للخدمة.
