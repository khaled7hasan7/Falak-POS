# Falak POS — خطة التنفيذ بالمراحل

> الملف 4 من 5 · 12 أسبوعاً، 6 مراحل، فريق من 2–3. كل مرحلة تنتهي بشيء يعمل على جهاز حقيقي ومعيار إنجاز مقاس.
> يُقرأ مع الملف 01 (النطاق والصلاحيات) والملف 02 (قاعدة البيانات) والملف 03 (التصميم).

---

## 1. الفريق والأدوار

| الرمز | الدور | المسؤوليات | إن كان الفريق شخصين |
|---|---|---|---|
| **A** | Backend & Cloud | قاعدة البيانات، الوكيل المحلي (API)، الترخيص، المزامنة، السحابة، لوحة فلك، الترحيلات، الأمان | يأخذ مهام C التقنية (المثبّت، الطابعة) |
| **B** | Frontend & POS | نظام التصميم في الكود، شاشة الكاشير، شاشات الإدارة، الترجمة، لوحة المالك | يأخذ مهام C في الاختبار والتوثيق |
| **C** | Hardware, QA & Field | الأجهزة (ماسح، طابعة، درج، ميزان)، Tauri والمثبّت، الاختبار اليدوي، التركيب عند العملاء، المحتوى والتسويق | — |

C بدوام جزئي حتى الأسبوع 7 ثم كامل. لو الفريق شخصان: المدة تصبح **16 أسبوعاً** بنفس الترتيب (المراحل 3 و4 تمتد أسبوعاً إضافياً كل واحدة، والتجربة الميدانية 3 أسابيع).

**مالك القرار:** خالد (المنتج والأولويات). أي خلاف تقني بين A وB يُحسم بما هو أبسط ويشتغل على الجهاز الضعيف.

## 2. هيكل المستودع

```
falak-pos/                     (pnpm workspaces + turborepo)
├─ apps/
│  ├─ pos/          React + Vite: الكاشير والإدارة (تُبنى static وتُقدَّم من الوكيل)
│  ├─ agent/        Node.js + Fastify: API محلي، طباعة، ترخيص، مزامنة، تحديث ذاتي
│  ├─ desktop/      Tauri 2: النافذة، الأيقونة، المثبّت، تشغيل الخدمات
│  ├─ cloud/        Node.js + Fastify: ترخيص، اشتراكات، إصدارات، مزامنة، نسخ احتياطي
│  ├─ admin/        React: لوحة تحكم فلك الداخلية
│  └─ owner/        React (PWA): لوحة المالك من الموبايل (قراءة)
├─ packages/
│  ├─ db/           Drizzle schema + migrations (من الملف 02)
│  ├─ ui/           tokens.css، المكوّنات، الخطوط (من الملف 03)
│  ├─ core/         منطق الأعمال المشترك: حساب الفاتورة، الخصومات، الضريبة، العملات، باركود الميزان
│  ├─ i18n/         ar.json, en.json, terms.*.json
│  ├─ printing/     ESC/POS، قوالب الفاتورة، ZPL
│  └─ contracts/    أنواع الـ API المشتركة (zod schemas)
├─ docs/            هذه الملفات الخمسة + ADRs
└─ tools/           سكربتات: بناء المثبّت، توقيع الحزم، seed
```

## 3. قواعد العمل

- **الفرع `main` يعمل دائماً.** كل مهمة فرع `feat/…` أو `fix/…`، مراجعة من شخص آخر قبل الدمج، CI يشغّل الفحص والاختبارات.
- **اختبارات إلزامية** على: حساب الفاتورة (packages/core)، التريجرات والاستعلامات الحرجة (packages/db مع PostgreSQL في CI)، الترخيص (apps/agent). الواجهة: اختبار واحد على الأقل لمسار البيع الكامل (Playwright).
- **جهاز كاشير حقيقي على المكتب** من الأسبوع 3: ويندوز 10، 4GB RAM، ماسح، طابعة حرارية 80mm، درج. ما لا يعمل عليه غير منجز.
- **عرض يوم الجمعة** لصاحب محل حقيقي (15 دقيقة) كل أسبوع من الأسبوع 4: نسجّل ما لم يفهمه.
- **الاجتماع اليومي** 10 دقائق: ماذا أنجزت، ماذا يعيقك. الأربعاء: مراجعة الأسبوع وتعديل الخطة.
- **قرارات معمارية** تُكتب كـ ADR قصير في `docs/adr/`.
- **تعريف "منجز":** يعمل على الجهاز الحقيقي + اختبار + مراجعة + ترجمة + يعمل في الوضع الداكن + مدمج في `main`.

بالترتيب حسب طلب العملاء الفعلي، وليس تخميناً: الفروع المتعددة الكاملة (مزامنة ثنائية الاتجاه)، ربط الميزان بالكابل، تطبيق أندرويد للكاشير المتنقل، الفوترة الإلكترونية للأردن/السعودية، تكامل واتساب للفواتير، الولاء المتقدم، ثم المطاعم كنوع نشاط جديد.

## 7. المخاطر الخاصة بالتنفيذ

| الخطر | المؤشر المبكر | الإجراء |
|---|---|---|
| المرحلة M2 تتأخر (الكاشير أعقد مما بدا) | نهاية W3 بلا فاتورة مطبوعة | تقليص: تأجيل شاشة الزبون والعروض، B يترك الإدارة لـ C |
| المثبّت يفشل على أجهزة معينة | أكثر من جهاز واحد من ثلاثة يفشل في W6 | خيار بديل: مثبّت PostgreSQL رسمي صامت بدل المحمول |
| Defender يحذف الوكيل | تحذير SmartScreen في W6 | الشهادة اشتُريت في W5؛ وإلا تعليمات استثناء مؤقتة |
| C غير متاح في الوقت المطلوب | مهام 2.8/2.9 بلا مالك في W3 | A يأخذ الطابعة، B يأخذ الاختبار اليدوي، المدة +1 أسبوع |
| المحل التجريبي ينسحب | لا يستخدمه 3 أيام متتالية | محل بديل مجهّز مسبقاً من W8 |
| توسّع النطاق ("ونضيف كمان…") | مهمة جديدة بلا معلم مقابلها | تُسجَّل في backlog ما بعد 1.0، لا تدخل الإصدار |
